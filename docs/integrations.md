# Integrations

Rule: **no invented APIs**. "Official API" means one documented by the operator. Unknowns are listed as verification tasks. Every adapter lives in `Integrations.*` behind an interface, records each call (request ID, timestamps, outcome, no secrets) for audit, and has a fake implementation for tests and local development.

## 1. SEF — Sistem elektronskih faktura (Ministry of Finance)
| Aspect | Detail |
|--------|--------|
| Purpose | Import and verify seller invoices; monitor status changes (buyer approval, cancellation, storno, credit notes) |
| Official API | **Yes.** Public API with Swagger documentation; DEMO `https://demoefaktura.mfin.gov.rs` and PROD `https://efaktura.mfin.gov.rs`, base path `/api/publicApi` ([efaktura.gov.rs](https://www.efaktura.gov.rs/)). Exact endpoint names must be taken from the current Swagger, not from this document |
| Authentication | Company-generated **API key** (`ApiKey` header), environment-specific. Generated by the seller in SEF |
| Data exchanged | Read: sales invoice by ID, sales invoice list/IDs by date range, invoice status, UBL XML download. **We never call write endpoints** (send, cancel, storno). The adapter does not implement them |
| Frequency | On import; before listing; at acceptance and at signing (freshness rules INV-R4); then daily until the deal is Closed or the receivable is terminal |
| Failure handling | Timeouts 10 s; 3 retries with exponential backoff + jitter for 5xx/timeouts; no retry on 4xx. 401 → mark the org's SEF connection `Invalid`, notify Owners. If SEF is down at a freshness-gated step, the step is **blocked** (fail closed) and the user is told to retry |
| Audit | Each status observation is stored in `sef_status_history` with raw payload; UBL is stored with its hash |
| Legal/contractual | LQ-21 (third-party use of API keys), LQ-22, LQ-23, LQ-51 (key has no read-only scope) |
| Verify (task 000/008) | Whether a read-only key scope exists; rate limits; the exact status enum; how credit notes link to the original invoice; whether a factoring flag exists |

### 1.1 Findings from the DEMO Swagger (read 2026-10-13, SEF demo, spec `public_v1`)
Source: `https://demoefaktura.mfin.gov.rs/swagger/index.html` → `/swagger/public_v1/swagger.json` (publicly readable without login). A `public_v2` spec also exists (10 paths, none for sales invoices). Re-check against PROD before go-live.

**Read endpoints needed for task 010/011/020** (base `/api/publicApi`, header `ApiKey` on every call):
| Need | Method & path | Parameters | Response |
|------|---------------|------------|----------|
| Sales invoice by ID | `GET /sales-invoice` | `invoiceId` (int64, query) | `SimpleSalesInvoiceDto` |
| Sales invoice IDs by date | `POST /sales-invoice/ids` | `status` (string), `dateFrom`, `dateTo` (date-time, query) | `SalesInvoicesDto { salesInvoiceIds: int64[] }` |
| Status changes for a day | `POST /sales-invoice/changes` | `date` (date-time, query) | `SalesInvoiceStatusChangeDto[]` |
| Download UBL | `GET /sales-invoice/xml` | `invoiceId` | file stream |
| Signature | `GET /sales-invoice/signature` | `invoiceId` | file stream |
| Cheap key check | `GET /getEfakturaVersion` | — | `EfakturaVersionDto` |

`SimpleSalesInvoiceDto` fields: `invoiceId, globUniqId, comment, cirStatus, cirInvoiceId, version, lastModifiedUtc, cirSettledAmount, vatNumberFactoringCompany, factoringContractNumber, cancelComment, stornoComment, status`. Amounts, parties and dates are not in this DTO; they come from the UBL.

`SalesInvoiceStatusChangeDto` fields: `eventId, date, newInvoiceStatus, salesInvoiceId, comment, cirInvoiceId, subscriptionKey, stornoNumber, cirAssignmentChange, isSigned, isAutoAssigned`.

**Enums**
- `SalesInvoiceStatus`: New, Draft, Sent, Paid, Mistake, OverDue, Archived, Sending, Deleted, Approved, Rejected, Cancelled, Storno, Unknown.
- `PurchaseInvoiceStatus`: New, Seen, ReNotified, Deleted, Approved, Rejected, Cancelled, Storno, SendingInProgress, Unknown.
- `InvoiceTypes`: Regular, Credit, DebitNote, Prepayment. `DocumentType`: Invoice, CreditNote, DebitNote, Prepayment.
- `DocumentReferenceTypes` include `CreditNoteReferenceToInvoice`, `CreditNoteReferenceToPeriod`, `StornoInvoice`: credit notes reference the original invoice (or a period) through the UBL billing reference.

**Answers to the open verification points**
| Point | Finding |
|-------|---------|
| Exact status enum | Answered (above) |
| Credit note → original invoice | Via UBL document reference; a credit note may also reference a **period** instead of a single invoice (needs handling in faceValue calculation) |
| Factoring flag | Partly: the invoice DTO has `vatNumberFactoringCompany` and `factoringContractNumber`, and error code `InvoiceForFactoringNotFound` exists. Who sets these fields and how is **not documented** in the spec → LQ-22 stays open |
| Read-only key scope | **Not found.** The same `ApiKey` grants write operations (`/sales-invoice/cancel`, `/storno`, `DELETE /sales-invoice`, UBL upload). See LQ-51 |
| Rate limits | Not in the spec. Ask SEF support |

**Write endpoints present in the API that our adapter must never implement:** `POST /sales-invoice/ubl`, `POST /sales-invoice/ubl/upload`, `DELETE /sales-invoice`, `DELETE /sales-invoice/{invoiceId}`, `POST /sales-invoice/cancel`, `POST /sales-invoice/storno`, `POST /purchase-invoice/acceptRejectPurchaseInvoice`, and all CIR, VAT-recording and company-update writes.

**Test access (DEMO):** the spec is public; an API key requires a company registered on the demo by its legal representative (eID). Full status-flow testing (buyer `Approved`/`Rejected`) needs **two** demo companies: one seller and one buyer.

## 2. CEF — Centralna evidencija faktoringa (Ministry of Finance)
| Aspect | Detail |
|--------|--------|
| Purpose | Check whether an invoice is already assigned; register assignments (or support users in doing so) |
| Status | **Not operational** as of 2026-10-05 (tender closed 2026-07-20; statutory deadline ≈ June 2027). The bylaw on technical details has not been published |
| Official API | Unknown. The law requires automated data exchange with SEF and high-assurance eID for users |
| MVP implementation | `ICefGateway` with a `CefNotOperationalGateway` that returns `NotApplicable`. The deal records this automatically. A manual-evidence path (`Registered` with reference + screenshot/PDF) is ready for when the CEF opens before the API integration exists |
| Future | Lookup before listing and before signing (block if assigned); registration by the seller via redirect or API (LQ-18) |
| Failure handling (future) | Fail closed for checks; registration failures leave `CefRegistration=Failed` and alert both parties (statutory deadline) |

## 3. APR — Agencija za privredne registre
| Aspect | Detail |
|--------|--------|
| Purpose | Company data, legal representatives, status; beneficial-owner register (CESV); **Registar faktoringa** for factoring-company approvals (regulatory.md S9) |
| Official email | The company's email for official correspondence recorded in APR is the channel for out-of-band notices and confirmations (ADR-020). *Verify that it is present for every company type*; fallback: letter to the registered seat |
| Official API | Public web search exists. Machine access: APR offers data services to registered users under contract (*verify scope, price, terms*). **Not assumed in the MVP** |
| MVP | Compliance officer looks up and uploads snapshots; structured fields entered manually with four-eyes for high risk |
| Future | Contracted data service, nightly refresh of status for active organizations and debtors |
| Legal | Terms of use for automated retrieval and storage; personal data in representative/BO records (LQ-34) |

## 5. Banking / payments
- **MVP: none.** The factor pays the seller via its own bank. The platform records reports and confirmations (ADR-004).
- Future options (each needs legal review LQ-07/LQ-08): IPS QR payment-order generation for fee invoices; bank statement import (camt.053) for **our own** fee collections; partner-bank escrow.

## 6. Identity / KYC providers
- MVP: none (manual KYB, local sanctions lists).
- Future: eID.gov.rs / ConsentID high-assurance login (also needed for the CEF), a video-identification provider, a sanctions/PEP provider. Select via an RFP covering data location, API, pricing, and Serbian law compliance.

## 7. E-signature
| Aspect | Detail |
|--------|--------|
| Purpose | Signing the factoring agreement (and possibly declarations) |
| MVP | Parties sign the PDF with their own **qualified** signature tools: smart-card or cloud QES from qualified trust service providers registered in Serbia. The platform **validates** PAdES signatures: integrity, certificate chain to a trusted Serbian QTSP root, revocation (OCSP/CRL), signing time, and signer identity vs. the organization's APR legal representatives or verified attorneys (ADR-020). Library: e.g. iText / DSS-based validation service (ADR-011) |
| Future | Integrated remote signing via a QTSP API |
| Legal | LQ-24 (required level), Serbian trust list source (Ministry's register of qualified trust service providers, *verify the format*) |

## 8. Email / SMS
- Email: transactional provider (Azure Communication Services Email) with SPF/DKIM/DMARC on our domain. Templates in Serbian (Latin) + English. No confidential document contents in emails, only links into the app.
- SMS: not in the MVP (MFA uses TOTP/WebAuthn). Future security alerts via a local SMS gateway.

## 9. Accounting (platform's own invoicing)
- MVP: monthly fee statement export (CSV) → our accounting system issues SEF invoices to payers.
- Future: issue fee invoices from the platform through **our own** SEF account via API (write scope limited to our company).

## 10. Integration audit requirements (all adapters)
Log: adapter, operation, correlation ID, organization, started/finished, outcome, HTTP status, retry count, and response hash or stored snapshot ID. Never log secrets or full personal data. Failures surface on the admin dashboard.
